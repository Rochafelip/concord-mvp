# DATABASE.md

# Database Architecture

## 1. Overview

The application uses PostgreSQL as the persistent source of truth.

The database stores the persistent state required by the Discord MVP:

* Users
* Servers
* Server memberships
* Channels
* Messages

Temporary and real-time coordination state may use Redis, but Redis must not replace PostgreSQL as the persistent source of truth.

---

# 2. Database Technology

## Primary Database

```text
PostgreSQL
```

PostgreSQL is responsible for durable application data.

## ORM

```text
Spring Data JPA
Hibernate
```

## Migration

```text
Flyway
```

All schema changes must be managed through Flyway migrations.

---

# 3. Database Principles

The database design follows these principles:

1. PostgreSQL is the source of truth.
2. Persistent data must not depend on Redis.
3. Foreign-key relationships should enforce data integrity.
4. IDs should be generated by the backend/database strategy consistently.
5. Timestamps should be stored consistently.
6. Soft deletion should not be introduced unless required.
7. Avoid premature database normalization when it adds unnecessary complexity.
8. Avoid storing derived data when it can be calculated reliably.
9. Do not store real-time media data in PostgreSQL.
10. Database migrations are immutable once applied.

---

# 4. Core Domain Model

The initial domain model is:

```text
User
 |
 +----< ServerMember >---- Server
                              |
                              +----< Channel
                                      |
                                      +----< Message
```

Relationship overview:

```text
User
 │
 ├─────────────── owns ────────────────> Server
 │
 └─────────────── belongs to ─────────> ServerMember
                                         │
                                         └────────> Server
                                                      │
                                                      └────────> Channel
                                                                    │
                                                                    └────────> Message
```

# 6. Users

Table:

```text
users
```

Stores application users.

## Suggested Schema

```text
users
--------------------------------
id
username
display_name
email
password_hash
avatar_url
created_at
updated_at
```

## Fields

### id

Unique user identifier.

Type:

```text
UUID
```

The application should use UUID identifiers consistently across the domain.

### username

Login identifier chosen by the user.

Requirements:

* Required
* Must not be empty
* Not required to be globally unique (`users.id` distinguishes accounts —
  see docs/DECISIONS.md D14)
* Maximum length should be defined by the API contract

### display_name

Name shown in the UI, independent of `username` (docs/DECISIONS.md D14).

Requirements:

* Required
* Must not be empty
* Maximum length should be defined by the API contract

### email

User authentication identifier.

Requirements:

* Required
* Unique
* Normalized before comparison/storage where appropriate

### password_hash

Stores the password hash.

Never store the original password.

### avatar_url

Optional URL referencing the user's avatar.

The MVP may use a placeholder avatar when no custom avatar exists.

### created_at

Timestamp when the account was created.

### updated_at

Timestamp when the account was last updated.

---

# 7. User Constraints

The following constraints should exist:

```text
PRIMARY KEY (id)

UNIQUE (email)

NOT NULL:
username
display_name
email
password_hash
created_at
updated_at
```

The database should enforce email uniqueness.

The application should also provide a user-friendly error when a duplicate email is attempted.

## Suggested Schema

```text
servers
--------------------------------

owner_id
created_at

```

## Fields

### id

Unique server identifier.

Type:

```text
UUID
```

### name

Server name.

Required.

### owner_id

References the user who owns the server.

Relationship:

```text
servers.owner_id
        ↓
users.id
```

### created_at

Server creation timestamp.

### updated_at

Last modification timestamp.

---

# 9. Server Ownership

Each server has exactly one owner in the MVP.

```text
Server
   |
   └── owner_id → User
```

The owner is also expected to be a member of the server.

The application must maintain this invariant.

---

# 10. Server Members

Table:

```text
server_members
```

Represents the relationship between users and servers.

A user can belong to multiple servers.

A server can contain multiple users.

Therefore, this is a many-to-many relationship.

```text
User
  |
  | 1:N
  v
ServerMember
  ^
  | N:1
  |
Server
```

## Suggested Schema

```text
server_members
--------------------------------
id
server_id
user_id
joined_at
```

---

# 11. Server Member Constraints

The following relationship must be unique:

```text
(server_id, user_id)
```

A user cannot be a member of the same server more than once.

Recommended constraints:

```text
PRIMARY KEY (id)

UNIQUE (server_id, user_id)

FOREIGN KEY (server_id)
    REFERENCES servers(id)

FOREIGN KEY (user_id)
    REFERENCES users(id)
```

# 13. Channel Type

Channel type should be represented using an explicit application enum.

Conceptually:

```text
TEXT
VOICE
```

The backend must not rely on arbitrary strings for channel behavior.

Example Java representation:

```text
ChannelType.TEXT
ChannelType.VOICE
```

The exact PostgreSQL representation may be:

* VARCHAR
* PostgreSQL ENUM

Prefer the option that keeps Flyway migrations and application evolution simple.

---

# 14. Channel Relationships

Each channel belongs to exactly one server.

```text
Channel
   |
   └── server_id → Server
```

A server can contain multiple channels.

```text
Server
   |
   +---- Channel
   +---- Channel
   +---- Channel
```

# 15. Messages

```text
messages
```

Stores persistent text messages.

## Suggested Schema

```text
messages
--------------------------------
id
channel_id
author_id
content
created_at
updated_at
```

---

# 16. Message Relationships

Each message belongs to:

* One text channel
* One user

```text
Message
   |
   +---- channel_id → Channel
   |
   └---- author_id → User
```

A channel can contain many messages.

A user can author many messages.

---

# 17. Message Constraints

Messages must contain:

```text
channel_id
author_id
content
created_at
```

The database should not allow empty message content.

The exact content-length constraint should be aligned with the API contract.

---

# 18. Message Ordering

Messages must be displayed chronologically.

The primary ordering mechanism should be:

```text
created_at
```

When timestamps can have the same value, the implementation should use a deterministic secondary ordering such as:

```text
created_at ASC
id ASC
```

This prevents inconsistent ordering.

---

# 19. Message Editing

Message editing is not part of the initial MVP.

The `updated_at` field may exist to support future evolution, but no editing behavior should be implemented solely because the field exists.

---

# 20. Message Deletion

Message deletion is not part of the initial MVP.

Do not introduce soft-delete columns such as:

```text
deleted_at
```

until message deletion becomes an actual product requirement.

---

# 21. Invitation Model

Decided in docs/DECISIONS.md D6 and D10.

Each server has exactly one active reusable invite code at a time.

## Suggested Schema

```text
server_invites
--------------------------------
id
server_id
code
created_at
```

## Constraints

```text
PRIMARY KEY (id)

UNIQUE (server_id)

UNIQUE (code)

FOREIGN KEY (server_id)
    REFERENCES servers(id)
```

`UNIQUE (server_id)` enforces "one active code per server" directly in the
schema — regenerating a server's invite is an `UPDATE` of its existing row,
not an `INSERT`, so the previous code stops resolving immediately (D10).

No expiration column, no usage-count column — not needed for the initial
MVP (D6).

---

# 22. Media Data

Audio, video and screen-sharing media must NOT be stored in PostgreSQL.

The database stores application state only.

Media flow:

```text
Browser
   |
 WebRTC
   |
LiveKit
```

PostgreSQL should never contain:

* Audio streams
* Video frames
* Screen frames
* Media packets

---

# 23. Voice/Video Session Persistence

The initial MVP does not require persistent call/session records.

A communication session exists primarily as real-time state.

Conceptually:

```text
Voice Channel
      |
      └── LiveKit Room
```

The mapping between an application voice channel and a LiveKit room should be deterministic or managed by the backend.

The exact implementation belongs to the media architecture.

Do not create a `calls` table unless persistent call history becomes a product requirement.

---

# 24. Redis Data

Redis is intended for temporary state.

Possible future data:

```text
Presence
Rate limits
Temporary session state
WebSocket coordination
Pub/Sub
```

Redis data should be considered ephemeral unless explicitly documented otherwise.

The application must not depend on Redis as the only storage location for critical persistent information.

---

# 25. Foreign Key Relationships

The core relationship graph is:

```text
users
  |
  +-----------------------+
  |                       |
  v                       v
servers              server_members
  |                       |
  |                       |
  +----------+------------+
             |
             v
          channels
             |
             v
          messages
             ^
             |
           users
```

Explicit relationships:

```text
servers.owner_id
    → users.id

server_members.server_id
    → servers.id

server_members.user_id
    → users.id

channels.server_id
    → servers.id

messages.channel_id
    → channels.id

messages.author_id
    → users.id
```

---

# 26. Delete Behavior

Deletion behavior must be deliberate.

The MVP should prefer preventing accidental cascading deletion of important data.

Recommended conceptual behavior:

```text
Delete User
    ↓
Not a normal MVP operation

Delete Server
    ↓
Hard-deletes messages, channels, members and invite code, in one
transaction (docs/DECISIONS.md D11)

Delete Channel
    ↓
Deletes or preserves messages according to explicit application rules
```

Do not add `ON DELETE CASCADE` to relationships automatically.

Every cascade must be intentional. The server-deletion cascade above (D11)
is the one deliberate exception, scoped to that specific operation.

---

# 27. Indexing

Indexes should support the application's most common queries.

Expected indexes include:

## Users

```text
UNIQUE INDEX users.email
```

## Server Members

```text
UNIQUE INDEX (server_id, user_id)
INDEX (user_id)
```

## Channels

```text
INDEX (server_id)
```

## Messages

```text
INDEX (channel_id, created_at)
INDEX (author_id)
```

Additional indexes should be introduced based on actual query requirements.

Do not create indexes for every column.

---

# 28. Message Pagination

Message history must support pagination.

The API should not load the entire message history of a channel in one request.

Conceptually:

```text
GET /channels/{channelId}/messages
```

should support pagination.

For large message histories, cursor-based pagination should be preferred over loading the entire dataset.

The exact API contract belongs in:

```text
docs/API.md
```

---

# 29. UUID Strategy

The application should use UUIDs for primary identifiers.

Examples:

```text
User ID
Server ID
Channel ID
Message ID
Server Member ID
```

Benefits:

* Globally unique identifiers
* Safer exposure through APIs
* Easier future distributed architecture
* Avoids predictable sequential public identifiers

The exact UUID generation strategy must remain consistent across the application.

---

# 30. Timestamp Strategy

All persistent timestamps should use UTC.

Conceptually:

```text
created_at → UTC
updated_at → UTC
joined_at  → UTC
```

The frontend is responsible for converting timestamps to the user's local timezone when displaying them.

The database must not store user-local timestamps.

# 33. Transaction Boundaries

Operations that modify multiple related records should be transactional.

Example:

```text
Create Server
    |
    +---- Create Server
    |
    +---- Create Membership
```

These operations should either:

```text
Both succeed
```

or:

```text
Both fail
```

The backend service layer should define the appropriate transaction boundary.

---

# 34. Message Creation Transaction

Creating a message should follow:

```text
Receive message
     ↓
Authenticate user
     ↓
Validate channel access
     ↓
Persist message
     ↓
Commit transaction
     ↓
Broadcast real-time event
```

The persisted database record is the source of truth.

The WebSocket event represents successful application-level delivery.

---

# 35. Real-Time State vs Persistent State

The system must distinguish between persistent and ephemeral state.

## Persistent

Stored in PostgreSQL:

```text
Users
Servers
Memberships
Channels
Messages
```

## Ephemeral

Handled by runtime infrastructure:

```text
WebSocket connections
Voice connections
Video tracks
Screen-sharing tracks
Presence
Media sessions
```

This distinction is important.

Do not create database records simply because a piece of runtime state exists.

---

# 36. Database Migration Strategy

Flyway migrations are append-only.

Example:

```text
V1__create_users.sql
V2__create_servers.sql
V3__create_server_members.sql
V4__create_channels.sql
V5__create_messages.sql
```

After a migration has been applied to a shared environment, it must not be modified.

Create a new migration instead.

Example:

```text
V6__add_avatar_url.sql
```

---

The initial database can be created progressively.

Recommended order:

# 39. Database Environment

Database configuration must come from environment variables.

Example:

```text
DATABASE_URL
DATABASE_USERNAME
DATABASE_PASSWORD
```

The application must not hardcode production database credentials.

---

# 40. Backup

Production PostgreSQL data must be backed up.

The initial MVP does not require an advanced backup architecture.

At minimum, establish:

* Automated database backups
* Retention policy
* Restore procedure

A backup that has never been tested for restoration should not be considered reliable.

---

# 41. Performance Principles

The MVP does not require database optimization for massive scale.

Prioritize:

1. Correct schema
2. Correct relationships
3. Correct indexes
4. Proper pagination
5. Efficient queries

Do not introduce:

* Sharding
* Read replicas
* Database partitioning
* Distributed databases

without actual performance requirements.

---

# 42. Database Anti-Patterns

The following practices should be avoided:

### Storing JSON for relational data

Do not store users, channels or messages as arbitrary JSON blobs.

### Duplicate source of truth

Do not maintain the same persistent data independently in PostgreSQL and Redis.

### Missing foreign keys

Relationships should be enforced by the database when appropriate.

### N+1 queries

Avoid loading related entities individually when a query can retrieve the required data efficiently.

### Loading all messages

Always paginate message history.

### Premature indexing

Do not index every field without a query requirement.

### Manual schema changes

Use Flyway.

# 45. Database Principle

The central database principle is:

> PostgreSQL stores what must survive; Redis stores what can be recreated.

In practical terms:

```text
PostgreSQL
    =
Users
Servers
Memberships
Channels
Messages

Redis
    =
Temporary state
Coordination
Caching
Rate limiting

LiveKit
    =
Audio
Video
Screen sharing
```

The database should remain simple, relational and understandable throughout the MVP.
